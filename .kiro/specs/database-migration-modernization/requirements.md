# Requirements Document

## Introduction

This specification defines the requirements for modernizing the database management approach in RuoYi-Vue3-FastAPI by migrating from a dual SQL file + Alembic system to a pure Alembic-based solution with Python seed data management. The goal is to establish Alembic as the single source of truth for database schema management, following best practices from FastAPI official templates and enterprise projects like GitLab.

## Glossary

- **Alembic**: A database migration tool for SQLAlchemy that manages schema changes through versioned migration scripts
- **Migration_Script**: A Python file generated by Alembic containing upgrade() and downgrade() functions for schema changes
- **Seed_Data**: Initial data required for application bootstrap (admin users, roles, permissions, system configuration)
- **SQL_File**: Legacy SQL files in ruoyi-fastapi-backend/sql/ directory used for database initialization
- **ORM_Model**: SQLAlchemy model classes in entity/do/ directories that define database schema
- **Docker_Container**: Containerized application environment that requires database initialization on startup
- **Idempotent_Operation**: An operation that produces the same result regardless of how many times it is executed
- **Migration_History**: Alembic's tracking of which migrations have been applied to a database

## Requirements

### Requirement 1: Initial Migration Generation

**User Story:** As a developer, I want to generate a complete initial Alembic migration from existing ORM models, so that I have a baseline schema definition in version control.

#### Acceptance Criteria

1. WHEN the initial migration is generated, THE Alembic SHALL create migration scripts for all existing ORM models (users, roles, menus, departments, projects, devices, protocols, simulations)
2. WHEN the initial migration is executed on an empty database, THE System SHALL create all tables with correct columns, indexes, and foreign key constraints
3. WHEN the initial migration is executed on an existing database with the same schema, THE System SHALL detect no changes and skip table creation (idempotent)
4. THE Migration_Script SHALL include proper upgrade() and downgrade() functions for rollback capability
5. WHEN generating migrations, THE Alembic SHALL use async SQLAlchemy configuration consistent with the application

### Requirement 2: Seed Data Management

**User Story:** As a developer, I want to manage initial data through Python scripts instead of SQL INSERT statements, so that seed data is maintainable and environment-aware.

#### Acceptance Criteria

1. WHEN the seed data script is executed, THE System SHALL create the default admin user with username "admin" and password "admin123"
2. WHEN the seed data script is executed, THE System SHALL create all system roles (admin, common user) with appropriate permissions
3. WHEN the seed data script is executed, THE System SHALL create the complete menu structure with proper parent-child relationships
4. WHEN the seed data script is executed, THE System SHALL create all dictionary data and system parameters
5. WHERE the environment is development, THE System SHALL include additional test data
6. WHERE the environment is production, THE System SHALL include only essential bootstrap data
7. WHEN seed data already exists in the database, THE System SHALL skip insertion to maintain idempotency
8. WHEN seed data script encounters an error, THE System SHALL rollback all changes and report the specific failure

### Requirement 3: Docker Integration

**User Story:** As a DevOps engineer, I want Docker containers to automatically initialize the database using Alembic, so that deployments are consistent and reproducible.

#### Acceptance Criteria

1. WHEN the backend Docker container starts, THE System SHALL execute "alembic upgrade head" before starting the application server
2. WHEN Alembic migrations complete successfully, THE System SHALL execute the seed data script
3. WHEN database initialization fails, THE Docker_Container SHALL log the error and exit with a non-zero status code
4. WHEN the database is already initialized, THE System SHALL detect this and skip redundant operations
5. THE Docker configuration SHALL NOT mount SQL files for database initialization
6. WHEN multiple containers start simultaneously, THE System SHALL handle concurrent migration attempts gracefully

### Requirement 4: Database Management CLI Tools

**User Story:** As a developer, I want convenient command-line tools for database operations, so that I can efficiently manage migrations during development.

#### Acceptance Criteria

1. WHEN I run "db_migrate.sh create <message>", THE System SHALL generate a new migration script with the provided message
2. WHEN I run "db_migrate.sh upgrade [revision]", THE System SHALL apply migrations up to the specified revision or head
3. WHEN I run "db_migrate.sh downgrade [steps]", THE System SHALL rollback the specified number of migrations
4. WHEN I run "db_migrate.sh current", THE System SHALL display the current migration revision
5. WHEN I run "db_migrate.sh history", THE System SHALL display all migration history with revision IDs and messages
6. WHEN I run "db_migrate.sh reset", THE System SHALL drop all tables, re-run migrations, and re-seed data
7. WHEN any command fails, THE System SHALL display a clear error message and exit with appropriate status code
8. THE CLI tool SHALL support both MySQL and PostgreSQL databases based on configuration

### Requirement 5: Seed Data Script

**User Story:** As a developer, I want a dedicated script to populate seed data, so that I can reset or initialize databases independently of migrations.

#### Acceptance Criteria

1. WHEN I run "seed_data.py --env dev", THE System SHALL load development seed data
2. WHEN I run "seed_data.py --env prod", THE System SHALL load production seed data
3. WHEN I run "seed_data.py --reset", THE System SHALL clear existing data before seeding
4. WHEN seed data insertion fails, THE System SHALL rollback the transaction and report which data failed
5. THE Seed_Data script SHALL use async SQLAlchemy sessions consistent with the application
6. THE Seed_Data script SHALL log each data insertion operation for debugging
7. WHEN seed data references foreign keys, THE System SHALL insert data in correct dependency order

### Requirement 6: Documentation Updates

**User Story:** As a new developer, I want updated documentation that reflects the Alembic-based workflow, so that I can quickly understand database management procedures.

#### Acceptance Criteria

1. WHEN I read README.md, THE Documentation SHALL NOT reference SQL file initialization
2. WHEN I read QUICK_START.md, THE Documentation SHALL include Alembic workflow instructions
3. WHEN I read the database migration guide, THE Documentation SHALL explain how to create, apply, and rollback migrations
4. WHEN I read the database migration guide, THE Documentation SHALL explain seed data management
5. THE Documentation SHALL include troubleshooting steps for common migration issues
6. THE Documentation SHALL include examples of creating migrations for schema changes
7. WHEN I read FAQ.md, THE Documentation SHALL address migration-related questions

### Requirement 7: Code Cleanup and Migration

**User Story:** As a developer, I want all references to SQL files removed from the codebase, so that the system consistently uses Alembic.

#### Acceptance Criteria

1. WHEN searching the codebase for SQL file paths, THE System SHALL return no active references
2. WHEN an error occurs that previously referenced SQL files, THE System SHALL display updated error messages pointing to Alembic commands
3. THE System SHALL move existing SQL files to sql/legacy/ directory for archival
4. THE System SHALL create a sql/legacy/README.md explaining the migration to Alembic
5. WHEN the application starts, THE System SHALL NOT attempt to load or execute SQL files
6. THE System SHALL remove any SQL file validation or checking logic from the codebase

### Requirement 8: Database Compatibility

**User Story:** As a system administrator, I want the migration system to support both MySQL and PostgreSQL, so that I can choose the appropriate database for my deployment.

#### Acceptance Criteria

1. WHEN using MySQL, THE Alembic SHALL generate MySQL-compatible migration scripts
2. WHEN using PostgreSQL, THE Alembic SHALL generate PostgreSQL-compatible migration scripts
3. WHEN database-specific features are used, THE Migration_Script SHALL include conditional logic for each database type
4. THE System SHALL detect the database type from configuration and apply appropriate migrations
5. WHEN switching between database types, THE Documentation SHALL explain migration considerations

### Requirement 9: Zero-Downtime Migration Strategy

**User Story:** As a DevOps engineer, I want to apply migrations without downtime, so that production systems remain available during updates.

#### Acceptance Criteria

1. WHEN a migration adds a new column, THE Migration_Script SHALL add it as nullable first, then populate data, then apply constraints
2. WHEN a migration removes a column, THE Documentation SHALL recommend a two-phase approach (deprecate, then remove)
3. WHEN a migration renames a column, THE Migration_Script SHALL use a temporary column approach to maintain compatibility
4. THE Migration_Script SHALL NOT include operations that lock tables for extended periods
5. THE Documentation SHALL include best practices for zero-downtime migrations

### Requirement 10: Backward Compatibility

**User Story:** As a system administrator, I want to migrate existing databases without data loss, so that I can upgrade systems safely.

#### Acceptance Criteria

1. WHEN running migrations on an existing database initialized from SQL files, THE System SHALL detect existing schema and skip redundant operations
2. WHEN the existing schema differs from ORM models, THE Alembic SHALL generate appropriate migration steps
3. WHEN data exists in tables, THE Migration_Script SHALL preserve all existing data
4. THE System SHALL provide a validation script to compare SQL file schema with Alembic migrations
5. THE Documentation SHALL include a migration guide for existing deployments

### Requirement 11: Migration Testing

**User Story:** As a developer, I want to test migrations before applying them to production, so that I can catch issues early.

#### Acceptance Criteria

1. THE System SHALL provide a test script that applies migrations to a temporary database
2. WHEN testing migrations, THE System SHALL verify that upgrade and downgrade operations are reversible
3. WHEN testing migrations, THE System SHALL verify that seed data can be loaded successfully
4. THE System SHALL provide a script to compare schema before and after migration
5. THE Documentation SHALL include migration testing procedures

### Requirement 12: Error Handling and Recovery

**User Story:** As a developer, I want clear error messages and recovery procedures when migrations fail, so that I can quickly resolve issues.

#### Acceptance Criteria

1. WHEN a migration fails during upgrade, THE System SHALL rollback the failed migration and report the error
2. WHEN a migration fails, THE System SHALL log the SQL statement that caused the failure
3. WHEN the migration history is corrupted, THE System SHALL provide a repair command
4. WHEN migrations are out of sync between code and database, THE System SHALL detect this and suggest resolution steps
5. THE Documentation SHALL include common error scenarios and resolution procedures
