# 统一数据库交付工作流 需求规格

## 简介

本规格定义一套覆盖开发、冻结、部署三个阶段的统一数据库交付工作流，用于消除“schema 变更、菜单/权限变更、字典/配置变更、发布可见性变更”分散在多条脚本与运行时机制中的现状。目标是让开发者和部署者只理解一套数据库工作流入口，在个人开发阶段获得“改完即可验证”的反馈，在冻结与发布阶段获得“正式产物可审计、可回放、可升级”的工程化保障，同时避免出现“功能已经修改但页面未生效、且无法快速定位”的情况。

统一数据库交付工作流的核心要求是：
- 所有数据库相关更新只通过统一入口触发，不再要求开发者分别理解旧的开发态 schema apply、bootstrap seed、菜单热同步、增量 SQL 补丁等多条旁路。
- 开发态与部署态共享同一套工作流模型，仅阶段职责不同，不允许机制割裂。
- 正式环境仍然只依赖 Git 中的正式交付产物完成升级，不重放开发态试错历史。

## 需求列表

### R1: 单一数据库工作流入口
**用户故事:** 作为开发者或部署者，我希望所有数据库相关更新都通过同一个工作流入口完成，以便降低理解成本并避免遗漏某条旁路导致功能未生效。  
**验收标准 (EARS):**
- R1.AC1: WHEN 开发者执行数据库相关操作 THEN 系统 SHALL 只暴露一个统一入口命令集，而不是要求分别执行 schema、菜单、seed、SQL patch 等多套脚本。
- R1.AC2: WHEN 数据库变更涉及 schema、引用数据或发布可见性 THEN 系统 SHALL 通过同一工作流编排这些步骤，而不是让调用者自行决定顺序。
- R1.AC3: IF 仓库内存在旧的数据库更新脚本或运行时同步机制 THEN 系统 SHALL 将其收编为统一工作流的内部实现，或阻止其继续作为面向开发者的独立入口存在。
- R1.AC4: WHEN 开发者或部署者查询当前数据库工作流状态 THEN 系统 SHALL 明确展示当前阶段、目标数据库、允许动作和受控范围。
- R1.AC5: WHEN 统一数据库工作流定义受管范围 THEN 系统 SHALL 区分“日常发布纳管数据”与“bootstrap 初始化数据”，并明确它们在开发同步、正式化和部署阶段的处理边界。

### R2: 开发态一致生效与失败前置
**用户故事:** 作为开发者，我希望在个人开发库中修改模型、菜单、权限、字典或配置后能通过一次统一同步立即验证结果，以便不再排查“为什么功能改了却没生效”。  
**验收标准 (EARS):**
- R2.AC1: WHEN 开发者在个人开发阶段执行统一开发同步动作 THEN 系统 SHALL 在同一次工作流中对齐 schema 与受管引用数据。
- R2.AC2: WHEN 开发者修改了会影响页面或接口行为的数据库声明 THEN 系统 SHALL 保证开发同步后结果足以直接验证页面和接口，而不要求再手动补跑其他脚本。
- R2.AC3: IF 统一开发同步中的任一步骤失败 THEN 系统 SHALL 以失败状态结束本次同步，并输出结构化错误报告，而不是静默保留旧状态继续运行。
- R2.AC4: IF 统一开发同步发现声明不合法、依赖缺失或目标态不可构建 THEN 系统 SHALL 在启动阶段或显式同步阶段立即阻断，而不是等到页面访问时才暴露异常。
- R2.AC5: WHEN 开发者处于开发阶段且显式允许快速同步 THEN 系统 SHALL 继续允许破坏性 schema 变更直接作用于个人开发库。
- R2.AC6: WHEN 开发者完成一次统一开发同步 THEN 系统 SHALL 提供可验证的状态反馈，说明 schema、引用数据、可见性控制是否全部已同步成功。
- R2.AC7: WHEN 第一阶段统一开发同步执行时 THEN 系统 SHALL 至少纳管 schema、菜单/角色菜单、字典/系统配置和发布可见性相关数据，以覆盖高频影响功能生效的数据库变化。
- R2.AC8: WHEN 开发者通过统一开发启动入口启动系统 THEN 系统 SHALL 在应用启动前默认先执行一次统一开发同步，并在同步失败时阻断启动，而不是允许开发者带着旧状态继续联调。

### R3: 冻结阶段正式化产物
**用户故事:** 作为需求负责人或开发者，我希望在需求冻结时将开发态最终结果整理为正式交付产物，以便进入协作、测试、预发、生产和客户升级流程。  
**验收标准 (EARS):**
- R3.AC1: WHEN 某项变更准备进入 Git 正式交付链路 THEN 系统 MUST 提供明确的正式化阶段，将开发态最终数据库变化整理为正式产物。
- R3.AC2: WHEN 执行正式化阶段 THEN 系统 SHALL 同时考虑 schema 变更与受管引用数据变更，而不是只正式化其中一部分。
- R3.AC3: WHEN 正式化阶段完成 THEN 系统 SHALL 生成可纳入 Git 和发布流程的正式交付产物，供后续部署阶段重复执行。
- R3.AC4: IF 当前代码状态不存在需要正式化的数据库差异 THEN 系统 SHALL 明确反馈“无待正式化变更”，而不是生成空产物或让操作者自行猜测。
- R3.AC5: WHEN 正式化 schema 变更 THEN 生成的正式 schema 产物 MUST 以当前正式 migration head 为起点，而不是以个人开发库的临时历史为起点。
- R3.AC6: WHEN 正式化阶段处理菜单、权限或其他功能可见性相关变化 THEN 系统 SHALL 生成独立的发布控制产物，以声明本次版本允许生效的可见性变更集合。
- R3.AC7: WHEN 正式化阶段生成发布控制产物 THEN 该产物 MUST 以仓库内显式文件的形式落盘并进入 Git 审查与发布流程，而不是仅存在于命令参数、运行时内存或外部平台临时状态中。

### R4: 部署链路零破坏收敛
**用户故事:** 作为部署者，我希望统一数据库工作流在收敛入口的同时不破坏现有上线与客户升级原则，以便平滑演进而不是重建整条部署链。  
**验收标准 (EARS):**
- R4.AC1: WHEN 统一数据库工作流引入部署态入口 THEN 系统 SHALL 保持“正式环境不执行开发态快速同步”的原则不变。
- R4.AC2: WHEN 测试、预发、生产或客户环境执行版本升级 THEN 系统 SHALL 仅依赖正式交付产物完成升级，而不重放开发态试错操作记录。
- R4.AC3: WHEN 新工作流接管部署入口 THEN 系统 SHALL 允许以兼容方式包裹现有部署脚本，避免一次性破坏当前上线流程。
- R4.AC4: IF 某次发布不存在受管引用数据或可见性产物 THEN 部署入口 SHALL 允许这些步骤以 no-op 方式通过，而不导致发布失败。
- R4.AC5: WHEN 新旧流程并存于过渡期 THEN 系统 SHALL 明确限制旧流程的适用边界，并提供淘汰路径，避免长期双轨运行。
- R4.AC6: WHEN 部署入口按顺序执行 schema、受管引用数据与发布控制产物 THEN 系统 SHALL 在任一步失败时立即停止后续步骤并返回失败状态。
- R4.AC7: IF 部署过程中某一步失败 THEN 系统 SHALL NOT 尝试对跨步骤的数据库变化执行全局自动回滚，而应依赖幂等正式产物、清晰的失败定位和明确的恢复指引继续处置。

### R5: 菜单与发布可见性统一纳管
**用户故事:** 作为产品或实施负责人，我希望菜单和权限既能在开发阶段完整验证，又能在部署阶段按发布策略控制是否对外可见，以便兼顾联调效率和上线可控性。  
**验收标准 (EARS):**
- R5.AC1: WHEN 菜单、权限或其他功能可见性相关数据发生变化 THEN 系统 SHALL 将其纳入统一数据库工作流，而不是作为独立同步流程存在。
- R5.AC2: WHEN 开发者在开发阶段执行统一开发同步 THEN 系统 SHALL 允许受管菜单与权限按声明同步到个人开发库，用于联调和验收。
- R5.AC3: WHEN 某项菜单或权限变化尚未获准随版本发布 THEN 系统 SHALL 支持在正式化阶段将其排除在本次发布控制产物之外。
- R5.AC4: WHEN 正式环境执行部署 THEN 系统 SHALL 只应用发布控制产物中声明允许进入本次版本范围的菜单与权限可见性变更。
- R5.AC5: IF 菜单或权限声明非法、父子关系缺失、发布策略冲突或受管边界不清 THEN 系统 SHALL 在统一工作流中阻断执行并给出明确定位信息。

### R6: 状态可观测性与问题定位
**用户故事:** 作为开发者或维护者，我希望系统能直接告诉我当前数据库状态是否干净、哪里未同步、哪一步失败，以便快速定位问题，而不是通过页面异常反推。  
**验收标准 (EARS):**
- R6.AC1: WHEN 开发者或部署者执行状态查询 THEN 系统 SHALL 输出 schema 状态、受管引用数据状态、发布可见性状态及最近一次工作流结果。
- R6.AC2: WHEN 统一工作流执行完成 THEN 系统 SHALL 输出分步骤结果摘要，包括成功、失败、跳过、耗时和目标数据库。
- R6.AC3: IF 工作流失败 THEN 系统 SHALL 输出可定位到声明文件、数据库对象或步骤名称的错误信息，而不是只返回笼统失败。
- R6.AC4: WHEN 开发者修改数据库相关代码但尚未完成正式化 THEN 系统 SHALL 能通过校验或状态命令明确指出存在未正式化差异。

### R7: 团队治理与旁路封禁
**用户故事:** 作为平台治理负责人，我希望所有数据库更新都能被统一校验和审查，以便阻止未纳管的变更流入共享环境和正式发布。  
**验收标准 (EARS):**
- R7.AC1: WHEN 代码进入 PR、主干、发布分支或正式构建流程 THEN 系统 MUST 校验当前代码与正式交付产物之间是否存在未正式化的数据库差异。
- R7.AC2: IF 检测到存在未正式化差异或旁路更新入口仍可被直接使用 THEN 系统 SHALL 阻止合并或发布，并要求先完成统一工作流正式化。
- R7.AC3: WHEN 新工作流进入稳态 THEN 系统 SHALL 持续阻断新增独立数据库更新入口回流。
- R7.AC4: WHEN 团队执行本地开发或 CI 校验 THEN 系统 SHALL 用一致的规则校验 schema、受管引用数据和发布可见性，不允许只检查其中一部分。

### R8: 长期维护场景下的双阶段并存
**用户故事:** 作为长期维护项目的开发者，我希望项目上线后仍能继续使用开发态快速验证，同时保持发布链路稳定，以便新需求探索和正式升级长期共存。  
**验收标准 (EARS):**
- R8.AC1: WHEN 项目已经存在正式 migration 历史并持续迭代 THEN 系统 SHALL 允许开发者继续在个人开发库中使用统一开发同步开展新需求探索。
- R8.AC2: WHEN 新需求从个人验证进入多人协作或发布阶段 THEN 该需求 MUST 再次经过统一正式化阶段，之后才能进入共享环境或正式环境。
- R8.AC3: WHEN 同一项目长期并存开发验证与正式发布两种阶段 THEN 系统 SHALL 保持统一入口和一致规则，而不是让不同需求重新发散出新的脚本或流程。

## Clarifications

### Session 2026-04-02
- Q: 是否要完全取消开发态快速 schema apply？ -> A: 不取消；保留开发态快速同步能力，但必须被统一工作流纳管，不能只覆盖 schema 而遗漏引用数据和功能可见性。
- Q: `menus.registry.yaml` 还有没有必要保留？ -> A: 可以保留为声明输入源，但不能再作为独立流程；必须由统一数据库工作流接管。
- Q: 统一后会不会影响上线部署流程？ -> A: 不改变“正式环境只依赖正式产物”的原则；以兼容方式收敛部署入口，避免破坏现有上线链路。
- Q: 菜单为什么不能继续在部署时直接按开发声明全量同步？ -> A: 因为正式环境需要发布控制；开发阶段可完整验证，部署阶段只应用获准进入本次版本的可见性变更。
- Q: 菜单/权限哪些进入本次发布，应由什么正式机制控制？ -> A: 使用独立的 `release manifest` 作为正式发布控制源；开发声明用于联调与正式化输入，部署阶段只应用 manifest 中批准进入本次版本的可见性变更。
- Q: 统一工作流第一阶段应纳管哪些引用数据？ -> A: 首批纳管 schema、菜单/角色菜单、字典/系统配置和发布可见性；用户、部门、岗位及其关系等 bootstrap 主数据保留初始化属性，不进入第一阶段的日常正式化发布范围。
- Q: 统一 `deploy` 的失败边界应如何定义？ -> A: 采用顺序执行、失败即停、不做跨 schema/data/visibility 的全局自动回滚；正式产物需保证幂等，并提供明确的失败定位与恢复指引。
- Q: `release manifest` 应由谁、以什么方式产出？ -> A: 由统一 `finalize` 阶段基于仓库内显式声明文件生成或更新仓库内的正式 manifest 文件；该文件进入 Git，部署阶段只认该正式文件产物。
- Q: 开发态 `dev-sync` 的触发方式应如何定义？ -> A: 统一开发启动入口在启动应用前默认自动执行一次 `dev-sync`，且同步失败必须阻断启动，避免开发者在旧库状态下继续联调。
