# 数据库双阶段工作流 需求规格

> 注：当前实现已经继续收敛，公开 CLI 使用 `scripts/db.py`，开发态公开入口为 `dev-sync`。本文记录的是较早阶段的双模式需求背景。

## 简介
本规格定义一套面向后端数据库 schema 演进的双阶段工作流，用于同时满足个人快速开发验证和多人协作/客户升级的稳定交付需求。工作流分为两种模式：个人开发阶段使用 `db push` 风格的快速同步能力，在个人独立数据库中优先保证“改完模型即可验证页面和接口”；进入协作、联调、测试、预发、生产或客户交付阶段后，统一切换到正式 migration 流程，保证数据库变更可审查、可追踪、可重复部署。

## 需求列表

### R1: 个人开发库快速同步模式
**用户故事:** 作为后端开发者，我希望在个人独立开发库中快速同步模型变更，以便优先验证接口和页面行为，而不是反复排查数据库未生效的问题。
**验收标准 (EARS):**
- R1.AC1: WHEN 开发者在个人独立数据库上处于 schema 原型阶段 THEN 系统允许执行 `db push` 风格的 schema 同步操作，而无需先生成正式 migration 文件。
- R1.AC2: WHEN 开发者完成 `db push` 风格的 schema 同步 THEN 数据库结构应与当前代码中的 ORM 模型保持一致，足以支持页面操作和接口联调验证。
- R1.AC3: IF 个人开发库被标记为可重建或可重置 THEN 系统允许开发者在该库上重复执行 schema 快速同步或重置操作，而不要求保留中间试错历史。
- R1.AC4: WHEN 开发者需要进入 `db push` 模式 THEN 系统必须要求开发者通过显式环境变量开启该模式，而不是默认自动进入。
- R1.AC5: WHEN 开发者已显式开启 `db push` 模式并通过项目启动脚本启动系统 THEN 启动脚本可在应用启动前自动执行一次 `db push`。
- R1.AC6: WHEN 开发者处于当前阶段的 `db push` 工作流 THEN 系统不要求持续监听模型变化并重复自动执行 `db push`。
- R1.AC7: WHEN `db push` 遇到删字段、改字段类型或其他破坏性 schema 变更 THEN 系统允许在个人开发阶段直接执行该变更，而不强制要求开发者改走正式 migration 或手动 reset 流程。

### R2: 共享与交付环境正式迁移模式
**用户故事:** 作为团队成员和发布工程师，我希望共享环境和客户交付环境只依赖正式 migration，以便避免个人试验性结构变更影响协作和部署。
**验收标准 (EARS):**
- R2.AC1: WHEN 某项数据库变更准备进入共享开发库、联调库、测试环境、预发环境、生产环境或客户现场数据库 THEN 团队必须将该变更整理为正式 migration，并以正式 migration 作为标准交付路径。
- R2.AC2: WHEN 共享或交付环境执行数据库升级 THEN 升级过程必须基于已提交到 Git 的正式 migration 历史完成。
- R2.AC3: IF 开发者未显式开启 `db push` 模式 THEN 系统默认禁止自动进行 `db push` 风格的 schema 变更。
- R2.AC4: WHEN 开发者未显式开启 `db push` 模式 THEN 系统默认使用正式 migration 工作流。

### R3: 阶段切换与正式化
**用户故事:** 作为需求负责人，我希望在模型逐步稳定后将个人开发结果正式化，以便进入多人协作和发布流程。
**验收标准 (EARS):**
- R3.AC1: WHEN 某项数据库变更准备进入 Git、共享环境、测试环境、预发环境、生产环境或客户交付 THEN 系统必须提供一个明确的 `finalize` 阶段，将当前最终 schema 变化整理为正式 migration。
- R3.AC2: WHEN 执行 `finalize` 阶段 THEN 生成的正式 migration 必须以“上一个正式发布版本的 migration head”为升级起点，而不是以个人开发阶段的临时同步历史为起点。
- R3.AC3: WHEN `finalize` 完成 THEN 团队后续在共享环境和交付环境中应只依赖该正式 migration，而不依赖个人开发阶段的 `db push` 操作记录。

### R4: 项目生命周期内的双模式并存
**用户故事:** 作为长期维护项目的开发者，我希望项目上线后仍能在新需求探索时继续使用个人快速验证模式，以便不把全项目永久锁死在单一工作流上。
**验收标准 (EARS):**
- R4.AC1: WHEN 项目已经存在正式 migration 历史且进入长期维护阶段 THEN 开发者仍可在个人独立原型库中继续使用 `db push` 风格的 schema 快速同步开展新需求探索。
- R4.AC2: WHEN 新需求从个人原型验证进入多人协作或发布阶段 THEN 该需求必须再次经过 `finalize` 生成正式 migration，之后才能进入共享环境或交付环境。
- R4.AC3: WHEN 工作流在同一项目的不同需求间切换 THEN 系统必须允许“个人库使用 `db push`、共享/交付库使用 migration”长期并存，而不要求整个项目只保留单一模式。

### R5: 开发者可见性与误用防护
**用户故事:** 作为开发者，我希望系统明确告诉我当前数据库处于哪种工作流模式以及为什么某些操作被拒绝，以便降低误操作和排查成本。
**验收标准 (EARS):**
- R5.AC1: WHEN 开发者执行数据库工作流命令 THEN 系统应明确展示目标数据库、当前模式（个人快速同步或正式迁移）以及本次允许执行的动作。
- R5.AC2: WHEN 开发者显式开启 `db push` 模式 THEN 系统按当前生效的数据库连接配置执行 `db push`，不额外进行共享库/受保护库识别或二次拦截。
- R5.AC3: WHEN 开发者修改了 ORM 模型但尚未将变更正式化 THEN 系统应提供可验证的状态反馈，帮助开发者判断当前数据库是否已同步或存在 schema drift 风险。
- R5.AC4: WHEN 开发者显式开启或关闭 `db push` 模式 THEN 系统应清晰反馈当前生效模式与对应风险边界，避免开发者自行推断当前工作流。
- R5.AC5: WHEN 启动脚本因 `db push` 模式在启动前执行一次 schema 同步 THEN 系统应清晰输出本次 `db push` 是否执行、执行结果以及未启用持续监听的边界。
- R5.AC6: WHEN `db push` 将执行破坏性 schema 变更 THEN 系统应在输出中明确提示本次变更将直接修改个人开发库结构。

### R6: 客户升级与发布可追踪性
**用户故事:** 作为运维或实施工程师，我希望客户现场升级只依赖正式 migration 产物，以便安全地从旧版本升级到新版本。
**验收标准 (EARS):**
- R6.AC1: WHEN 客户现场、测试环境、预发环境或生产环境执行版本升级 THEN 升级过程必须能够仅依赖正式 migration 完成，而不需要重放个人开发阶段的 `db push` 历史。
- R6.AC2: WHEN 某个版本包含数据库 schema 变更 THEN 该版本必须存在与之对应的正式 migration 产物，且该产物可被纳入标准发布流程。
- R6.AC3: IF 某项 schema 变更只在个人开发库中通过 `db push` 验证且尚未 `finalize` THEN 该变更不得进入客户交付或正式发布流程。

### R7: 团队治理与一致性校验
**用户故事:** 作为平台治理负责人，我希望系统能在团队协作前发现模型与正式 migration 的不一致，以便阻止未正式化的数据库变更流入共享环境和发布流程。
**验收标准 (EARS):**
- R7.AC1: WHEN 代码进入 PR、主干或发布分支 THEN 系统必须校验当前 ORM 模型与正式 migration 历史之间是否存在未正式化的 schema drift。
- R7.AC2: WHEN 检测到存在未正式化的 schema drift 且目标阶段已属于共享协作或发布流程 THEN 系统必须阻止合并或发布，并要求先完成 `finalize`。
- R7.AC3: WHEN 正式 migration 已生成并通过校验 THEN 团队可以按照标准 migration 流程在共享环境和交付环境中重复执行该变更。

## Clarifications

### Session 2026-04-02
- Q: 库类型应如何区分，避免开发者每次都要自己判断当前使用的是个人库还是共享库？ -> A: 环境变量显式切换；默认 migration，开发者手动开启 db push。
- Q: `db push` 应该如何触发？ -> A: 显式开启 db push 模式后，启动脚本启动时可自动执行一次 db push；当前阶段不做持续监听自动同步。
- Q: `db push` 遇到破坏性 schema 变更时应如何处理？ -> A: 允许直接执行，不额外拦截或要求 reset。
- Q: 如果显式开启了 `db push` 模式，系统是否需要识别共享库/受保护库并做二次拦截？ -> A: 不需要；开启 db push 后就按当前数据库连接执行，不额外做共享库识别。
