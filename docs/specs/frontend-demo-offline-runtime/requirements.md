# 前端离线演示 Runtime 需求规格

## 简介

当前前端已接入 MSW，并在开发环境通过 `fallback` 策略实现“真实服务优先、404/网络异常时回退到 Mock”的能力；同时项目存在真实 HTTP 与 WebSocket 业务链路，且客户前期演示希望直接部署演示专用静态产物即可完成页面访问、CRUD 操作与关键实时演示，不依赖额外真实后端。本需求旨在建立一套长期可维护的双模式运行体系：保留现有 `fallback` 作为开发联调兜底模式，同时新增 `demo-offline` 作为客户演示专用的纯前端离线运行模式；该模式需通过 MSW `pure` + Dexie/IndexedDB 本地持久化 + 场景包导入导出支撑 HTTP 与 WebSocket 演示，并尽量不侵入现有业务页面、API 调用和交互代码。

## 需求列表

### R1: 建立双模式运行体系
**用户故事:** 作为前端负责人，我希望同时保留开发态 `fallback` 与新增演示态 `demo-offline`，以便兼顾联调效率与客户演示稳定性。
**验收标准 (EARS):**
- R1.AC1: WHEN 应用以开发联调模式启动时 THEN 系统必须继续支持现有 `fallback` 语义，即真实服务优先，真实请求返回 `404` 或网络异常时回退到 Mock。
- R1.AC2: WHEN 应用以 `demo-offline` 模式启动时 THEN 系统必须以 `pure` Mock 方式运行，且不得访问真实 HTTP 或 WebSocket 后端。
- R1.AC3: IF 当前运行模式为 `real`、`fallback` 或 `demo-offline` THEN 模式选择必须显式可配置，且运行行为不得依赖隐式猜测或动态漂移。
- R1.AC4: WHEN 切换不同运行模式时 THEN 模式职责必须保持单一，`demo-offline` 不得复用 `fallback` 的降级逻辑作为主要能力。

### R2: 支持裸 `dist-demo-offline` 部署演示
**用户故事:** 作为售前或交付演示人员，我希望将 `dist-demo-offline` 部署到普通静态服务器后即可演示核心页面和数据操作，以便在前期无需真实后端即可向客户展示产品能力。
**验收标准 (EARS):**
- R2.AC1: WHEN 使用 `demo-offline` 目标构建前端产物时 THEN 输出的 `dist-demo-offline` 必须能够在 HTTP(S) 静态服务环境中独立运行。
- R2.AC2: WHEN 客户通过静态服务访问 `demo-offline` 的 `dist-demo-offline` 时 THEN 关键演示页面必须能够完成初始化加载、列表查询、详情查看与核心 CRUD 操作。
- R2.AC3: IF 页面刷新、关闭再打开或重新进入同一演示地址 THEN 已写入的演示数据必须可恢复，而不是仅存在于内存中。
- R2.AC4: IF 运行环境是 `file://` 直开页面而非静态服务 THEN 系统必须在文档中明确该方式不属于受支持部署方式。
- R2.AC5: WHEN 本期首批 `demo-offline` 能力交付时 THEN 覆盖范围必须限定为登录、菜单、首页、项目/版本相关核心 CRUD 与必要的实时展示能力，不包含仿真启动、暂停、停止等控制操作。
- R2.AC6: WHEN 用户进入 `demo-offline` 演示环境时 THEN 系统必须保留登录页与登录流程，并使用场景包定义的演示账号完成身份进入，而不是默认自动登录。

### R3: 保持对现有业务代码的低侵入
**用户故事:** 作为现有前端业务开发者，我希望新增演示运行时尽量不要求重写页面和 API 调用，以便控制改造成本和回归风险。
**验收标准 (EARS):**
- R3.AC1: WHEN 引入 `demo-offline` 运行时后 THEN 现有 `src/views/**` 页面、Store 和大多数 `src/api/**` 调用签名必须保持兼容。
- R3.AC2: WHEN 业务页面通过既有请求入口访问接口时 THEN 页面不应感知当前数据来自真实后端还是演示运行时。
- R3.AC3: IF 为支持离线演示需要新增运行时基础设施 THEN 新增逻辑必须集中收口于独立的 demo/mock 基础设施层，而不得将大量业务规则散落进页面组件。
- R3.AC4: WHEN 评估改造范围时 THEN 必须优先选择“修改启动层与运行时边界”而非“大面积重写业务页面”的方案。

### R4: 通过本地持久层支撑离线 CRUD
**用户故事:** 作为演示场景维护者，我希望离线演示数据能像真实系统一样被持久化管理，以便客户操作后刷新页面仍能看到一致结果。
**验收标准 (EARS):**
- R4.AC1: WHEN `demo-offline` 模式执行新增、编辑、删除、状态切换等操作时 THEN 数据必须写入浏览器本地持久层并在后续请求中可读。
- R4.AC2: WHEN 本地持久层初始化时 THEN 系统必须支持按版本创建、迁移和校验演示数据结构。
- R4.AC3: IF 首次打开演示模式或场景版本发生变化 THEN 系统必须能够自动导入默认场景数据并保证结果确定性。
- R4.AC4: WHEN 本期选择浏览器持久化方案时 THEN 必须采用 Dexie/IndexedDB 路线，而不得在本期需求中引入浏览器端 SQLite 或 PostgreSQL 作为必要前提。
- R4.AC5: WHEN 客户在 `demo-offline` 模式中执行数据操作后 THEN 结果必须持续保留，直到用户显式执行“重置场景”或切换场景，而不得因刷新页面或重新进入地址而自动清空。

### R5: 建立运行时分层以隔离网络、业务与存储逻辑
**用户故事:** 作为架构维护者，我希望演示运行时具备清晰分层，以便后续扩展场景、校验规则和 AI 生成数据时不产生结构性腐化。
**验收标准 (EARS):**
- R5.AC1: WHEN 演示接口被 MSW handler 拦截时 THEN handler 必须作为薄适配层，仅负责解析请求、调用业务服务并返回标准响应。
- R5.AC2: WHEN 业务服务处理演示逻辑时 THEN 业务规则必须通过独立 service 层编排，而不是直接堆叠在 handler 中。
- R5.AC3: WHEN service 访问演示数据时 THEN 所有本地数据读写必须通过 repository 层完成，而不是在多个位置直接操作 IndexedDB。
- R5.AC4: IF 后续更换本地存储实现、扩展场景或引入 AI 数据生成 THEN 上层 handler 与业务页面不应需要大面积重写。

### R6: 覆盖 HTTP 与 WebSocket 的关键演示链路
**用户故事:** 作为客户演示操作者，我希望不仅常规 CRUD 可用，关键实时能力也能被稳定演示，以便展示产品的完整业务链路。
**验收标准 (EARS):**
- R6.AC1: WHEN `demo-offline` 模式发起关键 HTTP 业务请求时 THEN 系统必须返回与现有页面预期兼容的响应结构。
- R6.AC2: WHEN 仿真或实时页面发起 `ws-ticket` 申请与 WebSocket 连接时 THEN 演示运行时必须提供可用的本地替代能力。
- R6.AC3: WHEN WebSocket 演示连接建立后 THEN 系统必须能够推送与页面当前消费模型兼容的状态、消息、带宽、告警、动画、故障和心跳事件。
- R6.AC4: IF 真实后端不可用且当前为 `demo-offline` 模式 THEN 关键实时演示链路不得因为缺少真实服务而中断。
- R6.AC5: WHEN 本期首批 `demo-offline` 实时演示能力交付时 THEN 必须采用预置只读演示流方案，而不是依赖用户触发仿真控制操作后才产生事件流。

### R7: 通过场景包支持演示切换与未来 AI 扩展
**用户故事:** 作为产品演示设计者，我希望通过标准化场景包切换业务数据，以便快速准备不同客户演示内容，并为后续 AI 生成场景提供稳定接口。
**验收标准 (EARS):**
- R7.AC1: WHEN 系统导入一个演示场景包时 THEN 必须能够批量初始化或重置与该场景对应的本地数据。
- R7.AC2: WHEN 用户切换演示场景时 THEN 系统必须以确定性方式替换当前演示数据，并避免新旧场景混杂。
- R7.AC3: IF 后续接入 AI 生成演示数据 THEN AI 产物必须落到统一的场景包格式，而不是直接修改 handler 或浏览器数据库内部结构。
- R7.AC4: WHEN 场景包格式演进时 THEN 系统必须保留显式版本信息和兼容校验机制。
- R7.AC5: WHEN 场景包定义演示账号、角色与菜单权限时 THEN 这些身份数据必须可直接用于 `demo-offline` 登录流程与登录后导航呈现。

### R8: 明确模式可见性、调试能力与文档约束
**用户故事:** 作为开发者和演示操作者，我希望明确当前运行模式、数据来源和受支持的使用方式，以便减少误用与排障成本。
**验收标准 (EARS):**
- R8.AC1: WHEN 应用运行在 `real`、`fallback` 或 `demo-offline` 模式时 THEN 开发者必须能够明确识别当前模式及关键数据来源。
- R8.AC2: WHEN 演示运行时拦截请求或切换场景时 THEN 系统必须提供足够的调试信息，以便定位行为来源和数据状态。
- R8.AC3: IF 文档声明支持某种运行模式、构建命令或部署方式 THEN 代码实现与脚本入口必须与文档保持一致。
- R8.AC4: WHEN 项目完成该能力交付后 THEN 文档必须清晰区分 `real`、`fallback` 与 `demo-offline` 的职责边界、适用场景和限制。

## Clarifications

### Session 2026-04-10

- Q: `fallback` 模式是否要作为本次改造的一部分被删除？ -> A: 不删除，保留为开发态“有服务走真实、无服务走 Mock”的兜底模式。
- Q: 裸 `dist-demo-offline` 演示是否允许依赖真实后端或额外独立 Mock Server？ -> A: 不允许，目标是部署到静态服务后可独立完成页面演示。
- Q: 浏览器本地持久化方案在本期采用哪条技术路线？ -> A: 采用 Dexie/IndexedDB，不在本期引入浏览器端 SQLite 或 PostgreSQL。
- Q: AI 生成 Mock 数据在本期的边界是什么？ -> A: 本期先定义标准场景包接口，为后续 AI 生成业务场景数据预留稳定输入输出格式。
- Q: 首期 `demo-offline` 的覆盖范围采用哪种方案？ -> A: 采用聚焦主链路方案，但不覆盖仿真启动、暂停、停止等控制操作。
- Q: 首期 WebSocket 演示策略采用哪种方案？ -> A: 采用预置只读演示流方案。
- Q: `demo-offline` 的登录方式采用哪种方案？ -> A: 保留登录页与登录流程，使用场景包定义的演示账号登录。
- Q: 演示数据被客户操作后的生命周期采用哪种方案？ -> A: 保留客户操作结果，直到用户显式重置场景或切换场景。
