# 前端 MSW 测试分层与一致性治理需求规格

## 简介

当前前端测试体系存在多类核心问题：开发环境主要依赖 MSW，而大量单元测试通过 `vi.mock` 直接替换 API/请求模块；错误场景覆盖不完整且缺少限流等边界；`src/mocks` 中存在较多 `@ts-nocheck`，导致类型约束弱化；部分测试只断言本地构造对象或 mock 调用，未验证真实请求链路；MSW README 给出 Node 测试接入方式但默认测试入口未统一落地。本需求旨在采用分层测试策略统一测试基线：不是“所有测试都走 MSW”，而是“HTTP 合约相关测试走 MSW，纯单元测试保留轻量 mock”，并以一次性切换方式治理存量问题，不引入兼容性双轨方案。

## 需求列表

### R1: 建立分层测试策略（B 方案）
**用户故事:** 作为前端研发负责人，我希望明确哪些测试必须使用 MSW、哪些测试可以使用 `vi.mock`，以便保证测试真实性与执行效率的平衡。
**验收标准 (EARS):**
- R1.AC1: WHEN 新增或修改涉及 HTTP 合约语义（状态码、响应体映射、错误处理链路）的 API/Store/Composable 测试时 THEN 必须使用 MSW 拦截请求并复用 `src/mocks` handlers。
- R1.AC2: IF 测试仅验证纯函数、纯状态变换或与 HTTP 合约无关的本地逻辑 THEN 允许使用 `vi.mock`/`vi.fn`，且不强制接入 MSW。
- R1.AC3: WHEN 测试边界不明确时 THEN 默认按“合约优先”归类到 MSW 测试，并在测试文件中保留分类说明。
- R1.AC4: IF 实施方案包含“旧测试路径 + 新测试路径”并行兼容设计 THEN 该方案必须被拒绝，并改为单路径目标态实现。

### R2: 统一 Vitest 与开发 Mock 行为基线
**用户故事:** 作为测试维护者，我希望 Vitest 与开发环境尽可能共享同一套 handler 行为，以便降低“测得过、跑不通”风险。
**验收标准 (EARS):**
- R2.AC1: WHEN Vitest 启动测试环境时 THEN 必须通过统一的测试生命周期初始化 MSW Server，并默认采用可复现的 `pure` 策略。
- R2.AC2: WHEN 执行 API 合约测试时 THEN 请求必须经过 `src/mocks` 场景路由与 handlers，而非直接 `vi.mock('@/utils/request')`。
- R2.AC3: IF 出现未被处理的网络请求 THEN 测试必须失败并输出可定位的错误信息。
- R2.AC4: WHEN 验证开发模式 `fallback` 语义时 THEN 必须覆盖 `withBackendFallback` 的三种路径：上游成功透传、上游 404 回退、上游网络异常回退。

### R3: 完整覆盖关键错误场景
**用户故事:** 作为业务开发者，我希望测试覆盖真实故障模式，以便在上线前发现异常路径回归。
**验收标准 (EARS):**
- R3.AC1: WHEN 编写或改造 API 合约测试时 THEN 每个核心模块至少覆盖 `timeout`、`5xx(含 503)`、`429` 三类错误场景。
- R3.AC2: IF handler 返回 `5xx` 或 `429` THEN 测试必须断言前端错误映射行为（消息提示、异常抛出或状态处理）符合既定逻辑。
- R3.AC3: WHEN 使用错误场景配置运行测试时 THEN 场景切换必须可显式控制并保持确定性结果。
- R3.AC4: IF 错误场景仅通过“手工构造错误对象并断言字段”实现 THEN 该用例不计入合约错误覆盖，必须补充真实请求链路测试。

### R4: 强化 mocks 类型安全
**用户故事:** 作为代码质量负责人，我希望 mock 工程具备编译期类型约束，以便减少隐式 `any` 和运行时数据形状错误。
**验收标准 (EARS):**
- R4.AC1: WHEN 执行类型检查时 THEN `src/mocks` 目录不得新增 `@ts-nocheck`，并逐步清理存量 `@ts-nocheck` 至 0。
- R4.AC2: WHEN factories 的输出结构发生变更时 THEN handlers 在编译期必须能感知并触发类型校验，而非静默通过。
- R4.AC3: IF 新增 mock 模块或场景 THEN 必须在共享类型定义中声明并导出对应类型契约。

### R5: 建立 CI 防回归门禁
**用户故事:** 作为项目维护者，我希望将测试策略与类型策略固化到 CI，以便长期稳定执行并防止回退。
**验收标准 (EARS):**
- R5.AC1: WHEN 任意分支提交合并请求触发 CI 时 THEN 必须执行 mock 策略检查脚本与前端严格类型检查，且规则立即生效。
- R5.AC2: IF 在 API 合约测试中检测到 `vi.mock('@/utils/request')` 等禁用模式 THEN CI 必须立即失败并禁止通过任何白名单例外。
- R5.AC3: WHEN 合约测试集或严格类型检查失败时 THEN 流程不得进入合并通过状态。
- R5.AC4: IF 任意分支存在禁用模式命中或门禁检查失败的提交 THEN 该分支对应合并流程必须被阻断，直到违规项清零。

### R6: 一次性全量迁移与结果度量
**用户故事:** 作为迭代负责人，我希望一次性完成全量迁移并有量化结果，以便快速收敛质量风险且不保留兼容路径。
**验收标准 (EARS):**
- R6.AC1: WHEN 启动迁移实施时 THEN 必须在同一治理周期内覆盖全部现存 API 合约测试模块，不允许仅做首批模块迁移。
- R6.AC2: IF 任意分支仍存在未迁移导致的门禁违规项 THEN 该分支不得通过合并，必须先完成迁移并通过门禁。
- R6.AC3: WHEN 全量迁移完成时 THEN 旧实现路径（例如合约测试中的 `vi.mock('@/utils/request')` 与相关兼容说明）必须被删除。
- R6.AC4: WHEN 完成迁移收敛时 THEN 必须产出结果报告，包含通过率、覆盖率变化与新增错误场景统计。

### R7: 治理低价值与伪测试
**用户故事:** 作为测试质量负责人，我希望清理“看似有覆盖、实际不验证行为”的测试，以便提升测试有效性与缺陷检出率。
**验收标准 (EARS):**
- R7.AC1: WHEN 用例仅断言本地拼装对象、常量或 mock 调用参数且未触发被测模块实际行为时 THEN 该用例必须重构为行为断言测试或删除。
- R7.AC2: WHEN 测试目标是 `@/utils/request` 或 `@/utils/http` 的错误映射逻辑时 THEN 必须通过真实模块调用触发拦截器分支，而非仅校验手工构造的 `AxiosError` 对象字段。
- R7.AC3: IF 用例被标记为“实现细节测试” THEN 必须在测试文件中注明其边界与存在理由，并避免被统计为合约覆盖能力。

### R8: 同步文档、入口与执行约束
**用户故事:** 作为团队协作者，我希望文档指引、测试入口和 CI 规则保持一致，以便新成员按文档即可复现实践。
**验收标准 (EARS):**
- R8.AC1: WHEN 文档声明了 MSW 在 Node/Vitest 的接入方式 THEN `tests/setup.ts` 与实际测试运行入口必须实现对应生命周期，不得仅停留在文档示例。
- R8.AC2: IF 更新测试策略或分层边界 THEN 必须同步更新 `src/mocks/README.md`、`tests/README.md` 与 CI 检查说明。
- R8.AC3: WHEN CI 发现文档约束与代码实现不一致（例如禁用规则未生效） THEN 必须阻断合并并提示修复。
- R8.AC4: IF 文档中仍保留兼容性或过渡性双轨指引 THEN 必须在本次治理中移除，仅保留目标态单路径实践。
