# 角色管理与双向授权最终交付核对

基线为 `std@991631e1b7947642612e023ca154c26a4c75d68f`。本轮整体核对发现并补齐一项 P2 角色写入契约交付遗漏。阶段实现、相关测试和独立候选检查已闭环；实际源目录另有一处范围外未提交改动导致全局类型检查失败，按要求保留，不能把源工作区表述为全绿。最终 std 交付及清理另见文末回执。

## 发现与修复

已提交客户端使用四个操作专用角色 DTO，但干净 std 的普通角色写入口仍接收内部 `AddRoleModel`。原页面发送完整表单的主流程正常；仅修改备注却省略 `menuIds` 会触发 500，省略 `deptIds` 会清空原关联，显式 null 和非法标量也与公开类型不符。独立首轮 FAIL 保留，不能用此前源目录或浏览器通过掩盖干净提交的缺口。

本次补交付四个公开输入 DTO，控制器按 `exclude_unset=True` 转为现有内部命令对象，服务按操作限制可写字段。省略关联字段保留，空数组或 null 清空；数据范围限定 1–5、状态限定 0/1，必需字段及跨操作字段在写入前校验。关系写入沿用现有事务；未恢复角色结果缓存或增设兼容入口。普通创建服务保持原实现。

四个入口的响应元数据与实际行为对齐：创建为 201，其余为 200，资源为 `RoleModel`。`shared/openapi.json` 只同步四个 operation、四个新 DTO schema，删除已无公开引用的 `AddRoleModel` schema。生成客户端仅替换四个 Responses 并补四个 Response 别名；使用锁定的 `@hey-api/openapi-ts@0.97.0` 临时生成结果核对，十二个相关输入/输出声明完全一致，其他类型声明不变。没有全库重新生成。

角色 VO 同时进行必要的 Ruff 类型语法整理；与原提交相比仅内部 Add/Edit 两模型的关系字段契约改变，其余八个模型 schema 一致；与原源目录相比全部十个模型 schema 一致，AST 证明只做等价类型语法及格式调整。源目录原有角色规则以及其他用户、部门、profile、密码改动均保留。
