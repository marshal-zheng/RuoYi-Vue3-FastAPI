# 定时任务 HTTP 写入契约

本轮完成定时任务新增、编辑、停启用和立即执行的输入隔离、服务端校验，以及请求失败时数据库与调度状态的恢复。范围限于这四个操作及其真实调用；ZXUI 源码未改动。

## 契约与业务行为

- 四个操作分别使用 `JobCreateModel`、`JobUpdateModel`、`JobStatusUpdateModel`、`JobRunModel`。新增必需名称、已注册调用目标和 Cron；编辑、停启用、执行必须提供正整数 `jobId`。未知字段、`type`、审计字段及新增携带客户端 ID 均返回现有 Problem Details 422。
- 编辑只允许任务配置及备注；未提供字段保留数据库原值。参数、备注允许 null/空字符串清空，结构字段和状态不接受显式 null。停启用只接收 ID/状态，立即执行只接收 ID，任务组和执行参数从数据库读取；审计信息由认证身份生成。
- 调用目标使用现有函数注册表；补齐页面已有示例函数的显式注册。复用现有 Cron 校验和实际 APScheduler trigger，使用真实参数转换校验函数签名、JSON 对象、任务存储和执行器。非法配置在写入前返回 422；目标任务不存在返回 404。
- 启用及正常编辑从合并后的完整配置创建调度；停用移除调度，也允许停用已有非法配置。换任务存储后只保留一份任务。保留原有位置参数拆分、关键字参数、并发、misfire，以及正常任务立即执行后继续定时、暂停任务只执行一次的语义。
- 前端 API 消费生成输入类型，生产表单显式提交业务字段，立即执行只传 ID。创建 201、编辑/状态 200、执行 202 及 Location、现有统一错误反馈保持原有契约；没有新增业务码白名单。

## 一致性修复与选择依据

旧实现可能因编辑未传状态而移除仍正常的调度，校验或提交失败也可能先破坏已有任务。本轮先验证有效配置并记录调度快照，数据库提交成功后才同步应用调度；调度应用失败时，先在任何 await 前同步恢复调度，再补偿已提交的数据库记录与审计字段。未成功提交的新配置不会提前执行。

独立复核进一步发现同任务并发请求可能让失败补偿覆盖另一笔成功修改。现已让编辑、停启用、执行在读取前取得同任务进程内互斥，持有至提交、调度及补偿结束；新增在取得生成 ID 后、提交前加入同一互斥。Repository 使用 `SELECT FOR UPDATE` 与 `populate_existing`，避免等待后继续使用 MySQL REPEATABLE READ 快照或 ORM 中的旧对象。原删除路径仅加入同任务互斥，未迁移其公开契约。

输入和局部更新复用已有 FastAPI/Pydantic 模式，依据 [exclude_unset 说明](https://fastapi.tiangolo.com/tutorial/body-updates/#using-pydantics-exclude_unset-parameter)。调度复用现有 APScheduler 3 的 ID、`replace_existing`、trigger 和 Job 参数检查，参见 [官方添加任务说明](https://apscheduler.readthedocs.io/en/3.x/userguide.html#adding-jobs)。没有新增依赖、通用调度框架或事务事件层；代价是同一任务的写入串行，以及调度失败时的一次数据库补偿。

这属于当前单进程运行方式下的请求级恢复，不承诺数据库与调度存储的跨系统原子事务。进程崩溃、多 worker 协调、持久调度存储持续故障或补偿本身失败未在本轮扩展。

- 前端聚焦 39 项通过；全局 ESLint、类型检查及 ZXUI 源码直连生产构建通过。保留既有 Browserslist 和大 chunk 提示。
- 40 项真实业务检查通过：生产任务页面 setup/确认、真实 API/统一反馈、源码 ZXUI hook/HTTP、Axios XHR、FastAPI、本地 MySQL、APScheduler 和 Redis job store。实际执行的是临时注册的无副作用函数，参数及调用次数均核对。
- 真实验证覆盖元数据污染、缺失/非法 ID、部分编辑保留、启停、已启用/已暂停任务立即执行、Redis 存储迁移、提交失败及调度应用后失败。并发用例在 MySQL `REPEATABLE-READ` 下先建立旧快照，确认等待互斥后的当前读恢复正确数据，失败请求与成功请求各产生一次相应反馈。
- 临时任务和任务日志已清理，原有任务/任务日志及用户、角色、岗位、部门列表与总数完全一致；没有未处理的 Promise 拒绝。错误保留 Problem Details、请求上下文，422/404/500 不误触发重新登录。
- OpenAPI 差异仅为四个请求输入、四个新 schema 和移除 `EditJobModel`；17 个契约/生成文件重复生成哈希一致。保留操作日志枚举的原有成员顺序，应用 schema 与 artifact 的语义检查通过。原始字节检查存在既有枚举顺序差异，检查证据明确只归一化 enum 成员顺序，没有忽略字段或约束。
- 新 Python 文件 Ruff 与格式检查通过，已有文件诊断无新增。后端约定脚本通过；前端约定脚本只被本轮未改动的 `VersionList.vue` 既有 console 用法阻挡。独立复核最终无阻塞发现。
