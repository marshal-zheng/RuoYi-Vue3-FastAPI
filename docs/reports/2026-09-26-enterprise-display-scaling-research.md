# 企业级显示大小：官方产品与开源项目调研

调研日期：2026-09-26。

本报告承接 [ZXUI × RuoYi 源码评估](./2026-09-26-zxui-ruoyi-display-scaling-assessment.md)。本轮查阅官方设计规范、产品帮助、组件 API 和选定开源实现；未操作这些产品的界面，也未实施 ZXUI/RuoYi 缩放功能。厂商行为与下文提出的 ZXUI 设计建议分别陈述。

结论：推荐保留「统一尺寸 token + 正常布局」方向，进一步形成「场景基准 + 经过校准的显示档位 + 组件尺寸配方 + 容器内布局规则 + CSS/JS 尺寸一致性」的完整能力。百分比是用户意图与基准比例，不能取代控件容纳内容、最小点击区域和视口边界等约束。用户已补充笔记本、台式机、电视、大屏场景，并确认电视/大屏同时需要展示与业务交互，见第 8 节。

## 1. 企业产品和项目实际怎么做

### Adobe Spectrum：尺寸档位由整套 token 支持

Spectrum Web Components 明确提供 medium/large 两套尺寸。其文档示例中，字体 16→19、控件高度 32→40、一个多行面包屑高度 72→84，变化并非每个值都严格乘同一系数；尺寸文件还包含间距和组件专属尺寸。它面向桌面与触控场景，不等同于低视力用户的任意比例缩放。[Styles / Scales](https://opensource.adobe.com/spectrum-web-components/tools/styles/)

平台设计规范还明确将边框宽度与其他尺寸变化分开。[Platform scale](https://spectrum.adobe.com/page/platform-scale/)

React Spectrum **v3** 的 Provider 提供 scale 与配置继承，可供自定义组件消费；这是具体版本的 API 证据。当前 Spectrum 2 的 Provider 页面没有相同的 scale 属性，不能把 v3 示例直接称为 S2 的现行接入方式。[v3 Provider](https://react-spectrum.adobe.com/v3/Provider.html)、[Spectrum 2 Provider](https://react-spectrum.adobe.com/Provider)

**可借鉴：**可缩放值、固定值、组件专属值有明确归属；业务通过公开配置接入。我们无需复制 Adobe 的具体像素，也不能假设其两个平台档位已经解决所有个人视力需求。

### SAP Fiori：密度与内容适配各有职责

Fiori 的 cozy/compact 主要服务触控与鼠标键盘。其规范说明 compact 下字号保持不变，控件尺寸和间距减少，并使用 rem 度量；密度要求在应用层统一设置。[Content Density，v1-120](https://www.sap.com/design-system/fiori-design-web/v1-120/foundations/visual/cozy-compact)

其工具栏有操作优先级和分组溢出机制；响应式表格可按列重要性把次要信息移到行内详情区域。这是显式内容语义驱动的适配。[Toolbar Overview](https://experience.sap.com/fiori-design-web/toolbar-overview/)、[Responsive Table](https://experience.sap.com/fiori-design-web/responsive-table/)

版本说明：上述工具栏/表格细节来自官方旧站可检索正文；新站 v1-145 工具栏页面此次仅能读取概要，没有把旧站细节声明为已逐项核对的新版本实现。

**可借鉴：**密度不能冒充全局显示大小；共享组件可统一处理溢出，业务提供重要性。适用于逐条查看的响应式表格与需要横向比较的分析表格，应采用不同布局策略。

### Salesforce Lightning：用户偏好与容器空间共同决定布局

Lightning 产品的 Comfy/Compact 会改变字段标签位置和页面疏密。其产品帮助也说明切换会 reload，因此它并非所有体验细节都适合照搬。[Personalize Lightning Experience Display](https://help.salesforce.com/s/articleView?id=user_overview_lex.htm&language=en_US&type=5)

更值得参考的是组件行为：Record Form 默认 density=auto，会读取用户密度设置及表单容器宽度；紧凑布局在窄容器中将标签移到字段上方。文档同时明确此能力适用于指定字段组件，表单内的自定义组件不会自动获得支持。[Record View Form / Form Display Density](https://developer.salesforce.com/docs/platform/lightning-component-reference/guide/lightning-record-view-form)

**可借鉴：**表单适配应发生在共享布局层，并依据自身可用空间。全局配置存在，不意味着任意自定义内容都已经适配。ZXUI 应明确消费者契约；RuoYi 应追求切档保留编辑状态，不复制 reload 行为。

### AWS Cloudscape：全局偏好与覆盖范围都是产品契约

Cloudscape 有 comfortable/compact 密度，官方推荐 comfortable 为默认；设置模式要求保存用户选择并跨服务内页面一致，且针对「部分功能支持」提供明确的呈现说明。[Density settings](https://cloudscape.design/patterns/general/density-settings/)

其 global-styles 包分别公开 applyMode 与 applyDensity 等帮助函数。[Global styles](https://cloudscape.design/get-started/for-developers/global-styles/)

**可借鉴：**主题、密度和显示大小保持清晰职责；默认值与个人选择有一致入口；迁移范围透明。该文档不构成 AWS 提供 90/100/110/125% 全局缩放的证据。

### AG Grid：行高由内容推导，虚拟布局读取真实尺寸

AG Grid 默认行高根据字体、图标和 padding 推导；垂直 padding scale 可以改变密度，同时保留字体变大时行高随之增长的行为。虚拟化依赖已知条目高度，文档要求使用正式参数或对应 CSS 变量，并通过测量变量获取尺寸。[Compactness & Row Height](https://www.ag-grid.com/react-data-grid/theming-compactness/)

源码中的 Environment 也通过 getCSSVariablePixelValue 读取行高、表头等有效尺寸，支持上述机制。[Environment 源码](https://raw.githubusercontent.com/ag-grid/ag-grid/latest/packages/ag-grid-community/src/environment.ts)

**可借鉴：**视觉与 JS 布局共享有效尺寸，不能 CSS 放大一遍、虚拟列表仍按旧常量计算。无需因此更换现有 VXE/EP 表格；应该为现有消费者提供同样清晰的适配路径。

### Microsoft VS Code：整体缩放与编辑器字号是不同设置

VS Code 有窗口 Zoom 命令和持久化 window.zoomLevel，同时另有 editor.fontSize 等内容字号设置。[Accessibility / Zoom](https://code.visualstudio.com/docs/configure/accessibility/accessibility)、[Settings examples](https://code.visualstudio.com/docs/editing/getting-started/tips-and-tricks)

本次核对的桌面源码调用 Electron webFrame.setZoomLevel，并同步内部缩放状态。[窗口缩放源码](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/platform/window/electron-browser/window.ts)

**可借鉴：**用户能找到统一入口、调整并恢复默认；内容区域与应用 UI 可以有不同语义。上述实现是桌面 Electron 路径，不能作为普通网页具有同样宿主 API 的证据，也不能据此推断 VS Code Web 的实现。

### IBM Carbon 与 Atlassian：按任务建立稳定的设计语言

Carbon 区分适合任务操作的 productive 排版和适合阅读探索的 expressive 排版，并强调同一任务/组件/区域内层级一致。[Typography strategies](https://carbondesignsystem.com/elements/typography/style-strategies/)

Atlassian 要求使用语义化的排版、间距 token，排版指导包含尊重浏览器默认字体的 rem 用法；间距规范将 token 作为后续响应式与密度能力的基础。[Applying typography](https://atlassian.design/foundations/typography/applying-typography)、[Spacing](https://atlassian.design/foundations/spacing)

**可借鉴：**ZXUI 应维护统一的文字角色、行高及空间节奏；产品开发者选择角色，避免逐页设计另一套尺寸。这些资料说明基础设施价值，没有证明这些产品已经提供同一种全局比例开关。

## 2. 调研后对上一轮方案的修正

1. **倍率公式只定义基准值，不直接定义最终控件高度。** 增加组件尺寸配方，协调文字行盒、图标、内边距、边框与点击目标；长内容可撑高。
2. **rem 本身是可靠工具。** 上轮对「只改根字号」的担忧来自当前项目还有大量 px 和 JS 常量，并非 rem 不适合企业系统。ZXUI 的多作用域与 Portal 要求决定其公开接口不能只依赖修改整个 document 的根字号。
3. **显示大小与布局变化联动，但各自有契约。** 文字大小由用户偏好决定；排列方式由容器、内容最小尺寸、显式优先级决定。空间不足时不能偷偷缩字。
4. **不承诺所有像素严格乘倍率。** 细线、点击目标下限、viewport 上限、业务画布坐标需要不同策略。四个比例可作为基准档位，但需明确受控件可用性与布局边界约束。
5. **覆盖声明必须与证据匹配。** 已支持组件、需要适配的第三方内容和未接入页面分别记录，迁移期间不能称为全系统已完成。

## 3. 建议 ZXUI 建立的统一模型

以下是针对本项目的设计推论，并非某个厂商的原样方案。

```text
使用场景的尺寸基准 + 用户显示偏好（90 / 100 / 110 / 125，默认 100）
             ↓
ZXUI 语义尺寸：文字角色、图标、空间、组件 size、density
             ↓
组件尺寸配方：内容容纳、交互方式对应的点击下限、明确的固定值
             ↓
布局规则：容器空间、字段最小宽度、操作/列优先级
             ↓
统一结果：普通 DOM、Portal、虚拟表格、图表 UI
```

颜色主题作为独立输入；displayScale 不应自动重置 density，也不必变成增加四倍编译组合的主题轴。首先复用既有 Host/Provider、主题消费和 revision 机制，避免引入第二个全局状态系统。

尺寸配方的示意：

```text
候选文字尺寸 = 当前场景下的角色基准文字尺寸 × 显示比例
候选控件高度 = max(文字行盒高度, 图标高度) + 上下内边距 + 边框
控件/命中尺寸 = 满足内容容纳与交互下限的尺寸
最终布局 = 在容器中按统一规则排列；不足时减列、溢出菜单或局部滚动
```

这是约束关系，不要求每个组件复用完全一样的公式。默认办公场景的 100% 要保持现有设计基准；远距离场景另行校准基准，并在设置中明确当前场景。90% 也要遵守可用性底线，不能把 12px 辅助文字、细小关闭按钮无条件再缩小。具体最小文字尺寸需产品校准，不能虚称 WCAG 规定了统一的最小字号。

输入方式与个人显示偏好也要分开：触控点击区域可以有自己的下限，但不能因检测到鼠标就覆盖用户的 125%。设置入口建议提供使用场景、四个显示档位与恢复当前场景默认值，内部保留 density、组件 size、输入方式的清晰职责；场景入口也可以由明确的「进入展示」操作承载。

## 4. 「智能适配」优先落在哪些共享能力

| 能力 | 建议规则 | ZXUI 与 RuoYi 分工 |
| --- | --- | --- |
| 控件与表单项 | 字体、行高、图标、padding 协同；说明/错误占据真实高度 | ZXUI 提供尺寸与行为 |
| 表单布局 | 依据缩放后的列最小宽度减列，必要时标签移到上方 | 先复用 RuoYi FormGrid；通用部分成熟后再提升到库 |
| 工具栏 | 次要操作按声明顺序/优先级进入更多菜单；保留键盘和焦点连续性 | 库统一行为，业务声明重要性 |
| 内容外壳 | Header、Sidebar、Tags、内容区共享尺寸来源；优先使用正常流和既有 fill 契约 | RuoYi 拥有外壳结构，ZXUI 提供基础布局能力 |
| 弹框/抽屉 | 尺寸预设可扩展，受 viewport 约束；正文与操作区有明确滚动规则 | ZXUI；业务声明表单列数/内容类型 |
| 表格 | 普通记录列表可考虑列详情；分析/编辑表保留横向比较与局部滚动 | 库/适配器提供机制，业务指定列语义 |
| 第三方与虚拟化 | 从正式接口获取有效像素、刷新缓存；不能只覆盖内部 CSS | 公共消费协议在 ZXUI，版本适配归对应集成层 |
| 新页面约束 | 使用文字/空间角色与共享布局；不再另写核心控件高度 | 文档、少量静态诊断与评审共同维护 |

普通业务不应为每个档位写四套 CSS。组件库也不能从 DOM 文本猜测「删除」与「保存」的重要性。长期复用依赖少量明确的业务语义和稳定的共享行为。

## 5. 三种可推进路线

| 路线 | 实施复杂度/投入 | 主要风险 | 适合程度 |
| --- | --- | --- | --- |
| A. 完整的比例尺寸迁移，布局仅补现有响应式 | 中高：仍要覆盖 token、EP、业务 px、JS；新增规则较少 | 长文、窄容器和多操作工具栏仍可能逐页修补 | 可以验证基础，不能作为长期目标的终点 |
| B. 四档显示大小 + 尺寸配方 + 共享适配规则 | 高：跨库契约与迁移；分批交付可控 | 组件局部样式、显式尺寸兼容、Portal/虚拟化同步 | **推荐，最符合多业务复用与长期维护目标** |
| C. 主要依赖浏览器原生缩放，项目集中修复响应式 | 初始低，完整响应式修复仍有投入 | 难以兑现产品内部独立四档偏好；浏览器控制粒度和 UI/内容边界不同 | 应保持兼容，适合作为用户已有辅助能力，不替代本需求 |

路线 B 可以先通过一条真实业务链路验证完整架构，然后按组件/消费者扩展。这里的阶段化是降低迁移风险，最终范围仍须覆盖约定的全局 UI，不能以演示页完成代替产品完成。

## 6. 对标成熟企业产品的验收标准

建议把「比肩顶级」落成可观察指标，而不是用厂商名称代替验证：

- **一致性：**同一显示档位下，库文档、业务页和 body 浮层使用同一尺寸契约；颜色主题切换不重置比例。
- **内容完整性：**长中文、英文、错误提示、长菜单在极端档位仍可读；不依赖 hover tooltip 才能完成关键操作。
- **任务连续性：**切档保留输入、选择、路由和必要焦点；被移入更多菜单的操作仍可发现、可用键盘访问。
- **布局稳定性：**选择有限、明确的响应式变化；避免临界宽度下反复换列/折叠或 ResizeObserver 反馈循环。
- **交互准确性：**虚拟表格末行可达、浮层位置正确、点击目标匹配可见控件；画布数据语义不变。
- **兼容性：**100% 默认基准、浏览器缩放/字体偏好、九个主题和明暗模式都有证据；新增业务可通过公开 API 接入。
- **可维护性：**尺寸归属、第三方适配范围、显式 px 逃生口和已知限制有文档；不靠业务覆盖 ZXUI 核心变量长期维持。

无障碍验收应包含文本放大、窄视口重排、文字间距变化和点击目标。WCAG 2.2 的相关说明分别覆盖 200% 文本放大、320 CSS px 的重排目标及例外、文字间距覆盖下内容不丢失、24×24 CSS px 点击目标或规定例外。应用内 125% 档位不能替代这些能力，也不能据本报告声明合规通过。[Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)、[Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)、[Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)、[Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

实施时先复用现有测试和真实页面：尺寸/继承/Portal/虚拟化只锁少量高价值契约；长内容、窄窗口和表单编辑流程做有针对性的验证。不要为接入新增庞大测试工程。

## 7. 建议的首条验证链与范围

先用真实用户管理页面串联：全局偏好 → Header/Sidebar/Tags → 筛选工具栏 → 表格/分页 → 多列表单弹框 → Select/Tooltip → 切档保留编辑状态。它能同时验证尺寸、布局、浮层和业务连续性。

之后补 VXE 协议编辑、图表 UI 与仿真工具控件。页面必须继续直连 ZXUI 源码；库问题在库里修复，业务布局问题在业务层修复。四档数值与目标先保留，具体尺寸配方应在真实字体、中文内容和典型窗口宽高下校准。

仍需在正式设计收敛的事项：仿真专用 UI 的首批范围、偏好按当前设备还是账号同步、旧 size Cookie 的迁移、可缩放默认值与显式尺寸的兼容策略。它们不影响本轮推荐 B 的方向，但会影响实施边界。

## 8. 多终端与多使用场景补充

用户已确认：产品用于笔记本、台式机、电视和大屏；电视/大屏既用于远距离展示，也需要遥控器或触屏参与业务操作，需要按场景切换。以下为据此收敛的设计建议，尚未实现或通过硬件验证。

### 官方参考与适用边界

Android TV 指南将约 3 米观看距离作为典型场景，建议采用远处可读的文字和元素、控制阅读负担，并强调方向键操作的明确反馈。[Design for TV](https://developer.android.com/design/ui/tv/guides/foundations/design-for-tv)

其焦点规范将可聚焦元素组织成逻辑分组，提供方向移动、选择和返回，以及清楚可见的焦点状态。[Focus system](https://developer.android.com/design/ui/tv/guides/styles/focus-system)

这些资料面向电视体验；本项目借鉴观看距离与输入方式的设计原则，不直接照搬原生平台单位、字体数值或媒体页面布局，也不把约 3 米当成所有客户的固定距离。

### 一个设计系统，分别描述场景、偏好与输入

| 维度 | 建议契约 | 对本产品的含义 |
| --- | --- | --- |
| 使用场景 | 先建立办公、远距离两类可校准基准 | 笔记本/台式机通常共用办公基准；电视/大屏由实际距离和任务选择场景 |
| 个人显示大小 | 四档相对于当前场景基准，偏好保持明确可见 | 远距离 100% 有自己的文字角色和尺寸配方；不能承诺桌面 125% 就足够远处阅读 |
| 输入方式 | 鼠标、键盘、触屏、遥控器可共存 | 同一块大屏可近距离触控，也可远距离遥控；输入变化不能暗中覆盖个人字号 |
| 可用空间 | 按实际内容容器的宽高、内容最小尺寸适配 | 自动减列、调整操作分组、限制弹框边界；充分考虑笔记本高度不足及超宽屏比例 |
| 页面任务 | 展示布局与操作布局复用业务数据和组件契约 | 看板突出指标/告警；完整业务操作保留表单、表格与编辑能力；远距离模式不强制只读 |

这些维度不全部暴露成用户设置，也不全部加入主题编译排列。颜色主题、尺寸场景、个人比例和交互行为应组合消费同一公开契约。

场景选择以明确的用户操作或部署默认值为依据。不用「4K」「屏幕宽度」或设备名称断言观看距离；分辨率相同不代表应该采用同一文字尺寸。操作系统缩放、浏览器缩放与产品偏好应兼容，产品不额外按设备像素比例重复放大界面。

### 全局能力与页面适配的边界

- **ZXUI：**拥有场景尺寸角色、显示比例、组件配方、交互目标、焦点呈现和公开尺寸消费协议；浮层、虚拟列表、图表 UI 消费同一有效尺寸。通用方向导航需明确焦点组和边界，不得抢走文本输入、Select 等控件自己的方向键语义。
- **RuoYi：**拥有场景入口、当前界面的偏好存储、外壳布局，以及展示/操作页面的信息层次。业务声明主要操作、关键表格列和关键指标，库不猜测重要性。
- **图表与业务画布：**图例、坐标文字、按钮和告警标签纳入可读性契约；数据坐标、拓扑结构或仿真尺寸保留领域含义，独立使用自身视图适配能力。
- **状态连续性：**切换比例或场景不刷新页面；保留输入、选择、筛选、必要滚动位置和焦点。需要改变页面组合时，编辑状态由稳定的业务状态承载，不能因组件重新挂载丢失。
- **遥控器：**可见焦点、可预测的方向导航、确定/返回、弹框焦点恢复、聚焦项滚入视野和无 hover 依赖要一起验证。仅有较大的按钮或 Tab 导航不足以宣称遥控器适配完成。
- **多窗口与共享屏幕：**建议显示偏好按本地使用场景保存，当前页面独立生效；大屏切档不强制改变另一窗口正在使用的办公界面。账号同步可提供默认偏好，但本地场景覆盖优先；不能承诺自动识别每一块物理显示器。

### 交付与验证顺序

1. 办公场景通过既定真实管理页面验证完整尺寸契约，并覆盖笔记本较低的可用高度。
2. 增加远距离基准，选择一个真实看板和一个完整业务操作流程，覆盖展示与交互两种用途。场景切换与四档比例都保持编辑状态。
3. 按目标交付环境验证触屏与遥控器。记录实际硬件/浏览器、有效视口、观看距离和输入设备，再校准文字角色、焦点和尺寸；仅模拟 4K 浏览器视口不能证明远距离可读性。
4. 针对超宽/拼接大屏，验证内容区域分配与关键告警可见性。布局由内容和容器调整，继续遵守不使用全页 transform 缩放的约束。

架构阶段现在就纳入上述维度；分批验证不等于将最终需求缩减为桌面四档开关。目标浏览器/遥控器按键能力与实际观看距离仍需在对应交付验证时确定，不在本轮凭设备类别编造统一数值。
